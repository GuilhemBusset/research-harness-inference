# Measuring how many students a pool can serve and what their agents can finish

**Proposed design.** Give the operator one skill invocation to open a GitHub experiment issue, book a bounded session on a deployed pool, exercise it through the student gateway, and post the results on the issue. The decision is specific to a class size, session shape, host count and serving configuration. A configuration qualifies when students receive usable streams **and** their agents complete the required tasks under that load. Among qualifying configurations, compare host cost per class-hour and time to a correct result.

## What we already know

The two one-host S5 runs used eight simulated students on a `g7e.2xlarge`. Here are their class-size rows, rounded. “First token” covers later turns. Both builds recorded zero preemptions and zero failed requests in these rows. A few deployment smoke requests overlapped the 4-bit run. [S5 record and run conditions](../measurements/s5.md)

| --- | ---: | ---: | ---: | ---: | --- |
| 8-bit | 1 | 80.20 | 22.73 / 15.92 | 5.19 | Fail |
| 4-bit | 1 | 91.36 | 26.26 / 15.85 | 3.62 | Pass |
| 8-bit | 2 | 83.13 | 17.03 / 6.84 | 22.98 | Fail |
| 4-bit | 2 | 96.92 | 17.42 / 9.48 | 42.57 | Fail |

The last row is the reason to run this experiment. It has the highest throughput in the table. The slowest 5% of measured later turns took about 43 seconds or longer to begin. S5 measures that experience with synthetic requests. S3 already gives real harnesses a Python optimization problem and checks the result. Its second exercise tests skills, PDFs, parallel agents and search. Those jobs produce different evidence and have different reporting paths. The missing piece is an experiment that repeats the same coursework on competing configurations and reads capacity and quality together. ## How the operator runs it

The proposed repository skill is **`$evaluate`** in Codex and **`/evaluate`** in Claude Code. The operator picks the pool, student count, host count and maximum booking duration. For example, this opens a new experiment issue and requests one host for up to three hours, including the capacity wait. The short screen runs as soon as the host is serving.

```text
$evaluate run --profile screen --pool coursework --students 8 --instances 1 --for 3h --issue new
```

One invocation covers booking, waiting, execution, grading, cleanup and posting the results. The model, instance type and engine configuration must already be deployed to the selected pool. Booking requests the specified number of hosts of that configuration through the existing scaler. Changing weights or vLLM settings for a candidate still goes through the project's deployment process. [Session runbook](../runbooks/sessions.md) · [Engine and image changes](../runbooks/image-and-engine-upgrade.md)

The proposed shared skill is a thin front end to `scripts/evaluate.sh`. Keep the invocation instructions in the repository's paired skill directories and the workflow in one tested controller. A Linux load driver outside the fleet runs the locked uv environment and trial containers. Its location, CPU allocation and network path stay fixed across comparisons. For invocation from a coding agent, an operator-started driver accepts a typed local request through an owner-only socket and returns the run ID, issue URL and status. The driver owns the operator's scoped AWS session and GitHub issue-writer access. The skill and student harnesses receive neither credential. Exiting the chat leaves the driver processing the run. An operator in a terminal can run the same controller directly.

```sh
# Preview work, time and host-hours offline
scripts/evaluate.sh plan --suite course-v1 --profile qualify --students 8 --instances 1

# Terminal equivalent of the skill invocation. course-v1 is the default suite.
scripts/evaluate.sh run --profile screen --pool coursework --students 8 --instances 1 --for 3h --issue new

# Use a dedicated session already booked by the operator. Add this run to its experiment.
scripts/evaluate.sh run --profile screen --pool coursework --students 8 --instances 1 \
    --session existing --issue "$experiment_issue"

# Re-read two saved bundles offline
scripts/evaluate.sh compare .cache/eval/reference .cache/eval/candidate
```

### Booking and running

1. **Plan and preflight.** Expand the ordered tasks, seeds, harnesses, arrivals and deadlines. Show cell counts, maximum simultaneous agents and identities, scratch space, host-hours and a conservative duration including drain and telemetry. Price the offline estimate with the example rate or a supplied rate and label its source. The driver checks the image and harness versions, writable local journal, available canaries, deployed pool limits, telemetry access and experiment destination. A `screen` runs one replay repetition and one attempt of each core task on the anchor harness. Reissuing canary keys remains an owner setup operation because it revokes the old ones. [Shared spike readers](../../spikes/common.py) · [Canary identities](../../admin/rhi_admin/spikes.py)
2. **Create the record, then book.** For `--issue new`, persist a unique run ID locally, create the issue and journal its number before requesting capacity. A positive `--for` selects managed booking and bounds the whole session. Use the deployed `max_instances` and `session_max_hours` and the same conditional booking primitive as the existing checks. Set a unique writer marker for the run, save the exact booking returned and request a scaler pass. If another booking already exists or wins the race, record `pool-already-booked` and stop. In `--session existing` mode the operator designates a dedicated booking. The driver checks its count and remaining time and leaves its lifetime to the owner. [Conditional book and stop](../../scripts/pipeline/booking.py) · [Scaler invocation and supply](../../admin/rhi_admin/session.py)
3. **Wait for the booked capacity.** Poll actual in-service count, gateway readiness and served release. One ready host is insufficient for a two-host measurement. Reserve enough of the window for the selected batch, drain and cleanup. If capacity arrives too late, record `capacity-unavailable` and release the owned booking. A missed capacity window gives an incomplete experiment. Model quality needs completed trials.
4. **Run and release.** Warm up, drive the sessions, grade and checkpoint the bundle. Monitor the booking, host membership and release throughout. On completion, error or cancellation, stop admissions, bound the drain, terminate trial containers and conditionally stop the exact booking this run created. Record cleanup status independently of measurement and publication. A concurrent operator edit causes the conditional stop to yield ownership. If the driver dies, the recorded end time bounds the booking and the scaler reconciles it. On restart, reconcile the journal against the actual record before resuming or cleaning up. A publication failure must never delay releasing capacity.
5. **Report.** Print the issue link, both verdicts, limiting rows and local report paths. Exit 0 for a completed profile meeting its applicable floors, 1 for a measured miss, 2 for invalid, incomplete or inconclusive evidence. Surface pending GitHub delivery separately. A standalone run establishes absolute performance and quality. A paired comparison provides the relative verdict.

A qualification plan can span bookings. `plan` prints the bounded batches and minimum window for each. `run --resume` reuses the issue and completed cells when their workload and serving identities match, and selects remaining whole cells that fit the authorized window. An interrupted cell starts fresh and retains its earlier partial attempt. Each new booking needs a duration in the operator's invocation. A single launch covers the plan when the window fits.

### Where results persist

Use **one GitHub issue per experiment**, with a comment per run and a final comparison comment when a candidate is compared. The issue body records the public experiment question, source commit, suite/profile, workload, target configurations, seeds and acceptance floors. An issue number on the invocation adds a run to the same experiment. The issue is an evidence record, outside the implementation backlog. Only an operator launch on the driver starts work.

Each terminal run comment includes the run ID, observed configuration, requested and served host counts, capacity and quality verdicts by class shape, p95 first token, p50/p10 stream speed, failures/attempts, task passes/attempts by harness, estimated host-hours, and cleanup outcome. Failed and interrupted runs get a comment with completed counts and a fixed reason. The local numeric bundle supports offline re-analysis. The comment carries its digest and, when exported through a PR, a permalink to the reviewed public bundle. A new checkout can read the headline results from the issue even when the original driver is gone. [Bundle and export format](#reproducing-and-comparing-runs)

Render issue bodies and comments from allow-listed fields and run the public hygiene scanner over the rendered text before sending. Publish relative durations. Keep actual booking times, class schedules, identifiers, raw tool output and prompts private. Persist the outbound comment and a run-ID marker before posting. After an ambiguous GitHub response, reconcile the marker against the driver's own issue or comments. A retry or resume targets the same record. If GitHub is unavailable before issue creation is confirmed, stop before booking. If it fails after the run, preserve the bundle and pending comment. A `publish --resume` replays delivery alone and requires no GPU.

## Workload and measurement protocol

Use two complementary experiments. **Replay** keeps the demands on the server repeatable as hardware and software change. **Live tasks** let a different answer cause a different tool call, different context and a different final result. Compare the replay with live tasks on the reference build before adopting a suite version. Tabulate p50/p90 input, output, cached fraction, tool delay, turns per task, route mix and observed fan-out by shape. If the research exercise spends most of its time in long subagent calls while the replay produces short replies, revise the fixture and remeasure the reference. A faster agent may genuinely need fewer turns. Show that benefit in task time and cost while measuring serving capacity on the controlled input.

| Phase | Proposed `qualify` workload | What it answers |
| --- | --- | --- |
| Driver check and warm-up | One streamed tool exchange per supported wire format, then short synthetic sessions until each host shows work. Use separate warm-up inputs and identities or prefixes. Verify telemetry coverage on every host. | Is the path usable and the engine warm? |
| Capacity sweep | Each shape at 1, 4, 8 and 16 agent slots, then at the requested class size. Deduplicate identical cells. Three repetitions with fixed distinct seeds. Use five minutes of admissions for diagnostic cells and 15 minutes for class-size cells, then drain for at most two minutes. A cell serving both purposes gets the longer duration. | Where does service first miss a floor? |
| Live tasks at low load | One student workspace at a time, with the fan-out required by the task. Exercise the pinned harnesses. | Can the serving configuration solve the work before contention? |
| Live tasks at class size | Run the same task instances on the same harnesses while the remaining seats sustain the corresponding replay shape. | Does successful work survive classroom contention? |
| Class opening | The target number of fresh student conversations starts on a seeded arrival schedule within one minute. Report first-turn p50/p95, failures and latest completion separately. | What happens when the instructor says “start”? |

For the sweep, reuse the S5 session planner and shapes. Hands-on means one serial agent per student. Several-agents means two independently advancing conversations sharing that student's key, concurrency limit, cache salt and gateway affinity. For a class of eight this is eight identities in both experiments, with eight or sixteen agent slots. Report observed concurrent requests and waiting requests alongside those slot counts. At a fixed number of agent slots, several-agents uses half as many identities rounded up. The 16-slot hands-on diagnostic needs 16 canaries even for an eight-seat class. [Session generator](../../spikes/loadgen.py) · [S5 planner, metrics and floors](../../spikes/s5_capacity.py)

Freeze a scrubbed request sequence per seed before comparing configurations. Start with S5's Messages profile, common 20k-token opening within a 50k–100k transcript, 1k–5k of new input per later turn, 500 requested output tokens and 5–10 seconds for tools. Preserve the growing prefix, documented tool schemas, calls and results from course fixtures. Use the recorded-session reader with canonical synthetic assistant and tool turns. S5's synthetic path feeds actual answer text into the next prompt, so its seed alone cannot freeze later inputs. Each replay still waits for its actual streamed response to finish before its next turn. A mismatch between a generated answer and the scripted next turn affects replay fidelity and earns no quality credit. Record requested and observed length distributions and finish reasons. Token counts come from served usage and vary by tokenizer. [Capture format](../../tests/captures/README.md)

Drive seats independently, including replacement conversations after completion. A slow seat must not hold up the start of another seat's next conversation. Precompute the opening times and tool delays, measure scheduling lag against *eligible* start times and report planned, started, completed and abandoned conversations. Subsequent turns remain causal.

At class size reserve one whole student seat for a live task, including its parallel tools or subagents, and fill the other seats with replay. With one seat the loaded and low-load trials coincide. Record peak fan-out and all side queries/retries at the gateway. Tag background and live traffic separately in the local driver. Finish each loaded trial before removing its background. Track the p95 delay from eligibility to dispatch and skipped starts independently of server latency. A skipped opening or driver scheduling lag above 250 ms at p95 invalidates the cell by default. Verify load-driver headroom against a local mock before the first live run, and version this tolerance in the suite.

Apply the same declared cache policy to reference and candidate. Start each repetition with a unique synthetic prefix namespace placed before reusable content and shared within that repetition as the class would share it. Keep the production per-student salt. Pair the exact prefix bytes across treatments. On a reused engine, use a disjoint canary cohort for the paired treatment or verify eviction before starting. Record the matched policy and count the keys needed in preflight. Verify the starting cache conditions using reported cache usage, and call the opening **fresh-prefix, warm-engine**. Other cached data can still occupy memory. Counterbalance candidate order across bookings where practical. If testing startup or an empty engine cache, require a separately booked fresh host and record the lifecycle evidence. Pair seeds across candidates, rotate cell order across repetitions, and keep class opening and warm-up samples out of steady-state summaries.

## Course quality and the grader

Version task prompts, fixture generators, tools, offline sources, expected properties and graders with the suite. Start with the four families below. For each, commit three distinct instances, including at least one changed input where a hard-coded exemplar answer fails. Keep grader fixtures and reference solutions outside the agent workspace. Before accepting a task, run its reference solution and a deliberately faulty solution against the grader. Use numerical tolerances and allow multiple optimal plans or equivalent artifacts.

| Family | What the student asks the agent to do | Observable pass condition |
| --- | --- | --- |
| Optimization model | Complete a broken HiGHS production-planning model and write the LaTeX plan. Change capacity and demand between instances. | Independent checks establish integrality, balance, capacity, objective against a reference optimum, and agreement between the solution and the table. Extend the [existing task and checker](../../spikes/s3_task/TASK.md). |
| Debug and revise | Run a supplied solver, diagnose its incorrect result, then adapt to a follow-up constraint in the same conversation. | The final program passes original and changed cases, and recomputing from its output satisfies the follow-up. |
| Parallel analysis | Delegate two parts of a supplied data analysis, combine them into a figure and explain a named comparison. | Independent workers overlap when delegation is required. Data, plotted series and axes correspond to the input, and the reported comparison agrees within tolerance. Adapt the [S3 figure exercise](../../spikes/s3_second_session/TASK.md). |
| Grounded research | Use a local search tool over a frozen packet of papers, including a PDF, to produce an evidence table and a short result. | Required facts, units, source IDs and cited page or table support the result. A plausible citation to the wrong table fails. The frozen packet makes the search result reproducible. |

Anchor coverage on Claude Code. Run all four families there. Run the two hands-on families on Codex and the production-planning instance set on OpenCode, Pi and the SDK tool loop. Keep the explicit task, harness and supported-feature assignments in the suite, including which harness can delegate. Every required cell in that table must finish. All traffic reaches the configured pool on the harness's normal route, including Messages, Responses and Chat Completions. Version the harness profile with the task and use the student-facing defaults for reasoning, request rewriting and context. [Pinned harnesses](../../spikes/harnesses.py) · [Student setup](../student-guide.md)

Each trial starts from a clean worktree-sized fixture in a disposable, resource-limited container. Mount only the task files and its pinned toolchain. Give the trial a fresh home, pinned tools and solver, a writable output directory, and access only to its own forwarding process and local fixture services. The forwarder injects the canary key outside the trial and streams responses. Keep cloud credentials, host configuration, container sockets, reference answers and the repository checkout outside. Enforce the task's published wall time, turn limit and output cap. Run submitted code in a fresh constrained worker and validate its outputs in a separate trusted grader. Discard trial homes and transcripts after grading. Reuse S3's command adapters and forwarder behavior with this isolation on an operator host.

At low load, run each task alone. At class size, use hands-on background for the optimization and debugging families and several-agents background for analysis and research. Run three attempts of each required instance/harness pair per load condition in the qualification profile. That is 27 instance/harness pairs × 3 attempts × 2 load conditions, or **162 trials per configuration** for a class with multiple seats. The proposed initial caps per trial are 12 minutes, 32 model turns across the agent tree and 32,000 total generated tokens. The controller enforces them at the proxy and trial supervisor, counting side traffic against the token cap.

At the time limit alone, 162 sequential trials could take 32.4 hours before replay and setup. Use the short screen first and batch full qualification by family and replicate. Pin a different cap before a comparison if the reference exercise needs it.

Launch a fresh agent for each attempt. Count an attempt as a success only when the grader accepts all required properties within its limits. A timeout, malformed tool call that prevents completion, or endpoint failure counts as a failed attempt. A broken grader or driver produces an invalid trial and an incomplete cell. Keep every attempt, including failed and superseded attempts. Resume replaces only invalid or interrupted trials, with the replacement linked to its predecessor. A completed failure remains in the denominator. Show successes/attempts, the fraction of instances with three successes in three attempts, failure reasons, task wall time, turns, retries and actual input/output tokens. Display quality by task family, harness and load so a failing research pack stays visible.

## Reading a result

| Decision | Rule |
| --- | --- |
| Capacity at the requested class size | For **each shape** and **each valid repetition**, later-turn p95 time to first token under the deployed limit, all-stream p50/p10 speeds at or above their floors, failed share at or below its cap and zero observed preemptions across all serving hosts. Current example values are 5 s, 15/10 output tokens/s and 0.5%. Read the deployed values once and store them. Flag the configured cached-share objective separately. |
| Absolute quality | Proposed starting floor of 80% successful attempts in each required family/harness cell, reported separately for low and class load. Treat this as a versioned course policy for calibration on the first reference run. |
| Relative quality | For each course shape and load, the lower 95% bound on the paired success-rate change must be at least −5 percentage points. A candidate can clear the hands-on comparison and fail the research comparison. |
| Class recommendation | Require all scheduled repetitions, capacity and both quality checks at the matching shape and load. Hands-on requires the optimization and debugging families. Several-agents requires analysis and research. Also show the equally weighted combined result. Report the smallest **tested** host count satisfying them at the requested class size for each shape. Report a common configuration only if it passes both. An uncovered class size or a larger untested fleet remains unknown. |

**How to compare quality.** Match task inputs, harnesses, seeds, background load and limits. At each load, average success over attempts of each instance, then over instances within a family/harness, then equally over harnesses in a family. Give the two families in each course shape equal weight, and give the two shapes equal weight in the combined result. Apply the absolute floor to every required cell.

Compute candidate minus reference on the matched observations. Use 10,000 seeded bootstrap draws, resampling task instances within each family and retaining all their harnesses. Within each sampled instance, resample matched repeat indices for both candidates together. Report the 2.5th and 97.5th percentiles of the differences. An interval wholly below −5 points fails. One spanning that margin is inconclusive. If every resample gives the same difference, report the observed difference and mark the precision inconclusive. A new paired series or more distinct tasks can resolve it. The proposed 80% floor and 5-point margin are course policy choices. Freeze them before the candidate runs.

Measure TTFT from send to the first output-bearing event, including reasoning or tool arguments. Also show time to the first non-reasoning output. Ignore pings. For a completed stream with at least two reported output tokens and distinct first/last output times, speed is `(output_tokens − 1) / (last_output_time − first_output_time)`. Show the count of eligible streams. Count truncated streams, transport errors, HTTP refusals and error events inside HTTP 200 in failed requests / all attempts. Verify route-specific stream termination. Record missing usage and sample coverage separately. Use the existing interpolated percentile definition. [Load generator](../../spikes/loadgen.py) · [Shared statistics](../../spikes/common.py)

For the whole cell, report engine output-token counter increase divided by elapsed seconds through drain, per host and summed across the pool. Show student-observed delivered output separately. Include successful tasks per elapsed hour of the live phase, task duration including tool waits, cached and computed input, queue depth, preemptions, GPU utilization, and cost per million generated tokens at the configured host price. Use elapsed instance-hours for cost per successful task, including failed work and background traffic during the loaded phase. When nothing succeeds, show the denominator and leave the ratio undefined. Mark cost as a host estimate. Compare task time and correctness across tokenizers as well as token rates.

For each steady class-size repetition require at least 100 eligible later turns for TTFT and 100 eligible streams for speed, along with complete accounting for attempts. Print numerator, denominator and variation across repeats. This minimum makes p95 interpretable as a sample statistic.

A measured failure fraction of zero over 100 attempts gives little assurance about a 0.5% failure ceiling. Show its count and interval, label the S5-style verdict as an observed floor, and let an operator predeclare longer confirmation runs. Include a Wilson 95% interval for failed share as a descriptive request-level interval and show the range across repetitions because failures can cluster within sessions. With three instances per task family the quality interval also describes a small fixed curriculum. Add distinct tasks when uncertainty about a model decision persists. Retain insufficient cells as inconclusive. Never combine repetitions to hide a missed floor.

## Reproducing and comparing runs

The bundle holds a schema-versioned `manifest.json`, append-only request and trial records, metric samples reduced to public fields, and derived `summary.json` and `report.md`. A fresh checkout can regenerate the reports offline from the bundle. Use run-relative monotonic times and local student, trial and host ordinals in exported evidence. Permit only enumerated labels, bounded numbers and vetted public digests. Keep generated work, paths, raw endpoint addresses, roster aliases, credentials, environment dumps and model text out of the bundle. Keep scratch under the ignored `.cache/eval/`. An explicit export writes a validated comparison and replayable numeric bundle under the proposed `docs/evaluations/` for review through a normal PR. The default issue-backed workflow persists the public scorecard even when the full evidence bundle stays on the driver. [Repository hygiene](../../AGENTS.md) · [Existing spike record convention](../measurements/README.md)

Record the clean source commit, suite and grader hashes, normalized workload/arrival manifest, seeds, dependency lock hashes, exact harness and driver image versions, limits, sampling settings, load-driver resources and path category. Record observed instance type/count, GPU type/count, model and tokenizer revisions, quantization, engine image digest, vLLM version, context limit, KV dtype, prefix caching, tensor parallelism, batch/step budget, speculative decoding, renderer/parser and gateway profile. Fingerprint allow-listed public settings only. Record configured and observed values separately.

The lifecycle metric already identifies the served image digest and model revision. Two runs can have both in common and use different flags. For flag experiments, add a fingerprint of the normalized arguments **actually launched on each host** to lifecycle telemetry, and match it to the manifest throughout the cell. Read effective settings from engine metrics where exposed. Include gateway release/profile provenance for request-side experiments. Until that evidence exists, label a flags-only comparison unverified. A release parameter read today describes desired state. [Release construction](../../src/rhi/pools/release.py) · [Serving telemetry](../../services/engine/lifecycle/rhi_lifecycle/serving.py)

After allowing for scrape delivery, verify membership and identity over the complete window, account for counter resets, and require preemption coverage on every host. Record gaps as missing. Detect other users or smoke traffic with aggregate gateway counter deltas over the pool and the canary cohort, reconciling cohort counts with driver attempts that reached the gateway. Include settling margins and exclude setup probes. The node's own periodic liveness completion is normal engine activity and remains in engine throughput. Flag overlapping external traffic, unreconciled counters, host turnover, driver saturation or missing required evidence as invalid for qualification. Keep the observations for diagnosis. A known miss on an otherwise valid measured cell still appears even when another cell is incomplete.

`compare` prints the configuration diff before the scorecard. Match workload and measurement protocol hashes, task and harness versions, cache policy, sample budgets and objectives. Allow declared treatment fields such as host count, model/tokenizer, quantization or step budget to differ. A change to a task or floor needs a new reference measured under that version. Vary one lever per experiment where possible and label combined changes as such. Use the same input and schedule seeds for each treatment and disclose any difference in realized load or output lengths. For cross-model comparisons show task completions per hour and emitted tokens per turn alongside tokens/s. Live outputs can vary across scheduling, hardware and vLLM releases. [vLLM reproducibility guidance](https://docs.vllm.ai/en/stable/usage/reproducibility/)

Start the first comparison with one and two hosts of the same build at the same eight-seat target. A several-agents p95 miss alongside queueing and otherwise good isolated quality makes this a direct scaling test. Then compare 8-bit and 4-bit at fixed host count with the same tasks. If long prefill stalls neighboring streams, test the vLLM step budget at fixed model and hardware and read both later-turn TTFT and p10 speed. A model or effort change can reduce the output needed to finish, so read successful task duration, pass rate and cost together. Report the measured trade-off and keep the existing configuration as the reference until a comparable candidate qualifies.

## Research behind the choices

- MLCommons' agentic inference methodology preserves causal turns, reuses recorded prefixes and pairs aggregate throughput with per-user progress and accuracy checks. We adopt those principles at the project's gateway, with its own affinity and per-student salt. [MLCommons agentic inference methodology](https://mlcommons.org/2026/07/agentic-inference-for-mlperf-inference/)
- NVIDIA's AIPerf models shared prompts, session-specific context, inter-turn delays and resets. Its trace format is a useful cross-check for our workload distributions. The existing replay code already handles our canary identities and wire formats. vLLM's serving benchmark supports request-level latency and goodput objectives and is a useful engine diagnostic. [AIPerf agentic dataset design](https://docs.nvidia.com/aiperf/tutorials/datasets-inputs/agentic-code-dataset-generator) · [vLLM serving benchmark](https://docs.vllm.ai/en/stable/cli/bench/serve/)
- Anthropic's agent evaluations distinguish a task, a trial and the resulting environment state. That distinction motivates checking solver feasibility, tables, figures and source grounding directly. Repeated trials expose failures a single successful demonstration would hide. [Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)
