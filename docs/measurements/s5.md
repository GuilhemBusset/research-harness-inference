Spike S5 (system design, section 12) asks what one coursework instance serves: every row of
section 4.7's table, with replayed agent sessions of both shapes, hands-on and several agents a
student, at 1, 4, 8 and 16 streams and at the class's size, on the 8-bit and the 4-bit build; the
cache size the engine reports at start; and what each lever of section 4.7 changes. Every number
of section 4.7 for the coursework pool is arithmetic until then. This record replaces that table,
and the dry-run class of phase 3 is judged against it (section 14).

If the class-size runs miss a floor, the answer is the levers of section 4.7 in order, then fewer
streams and more instances per session, or the upgrade pool.

## The job

The job `s5_capacity` runs [`spikes/s5_capacity.py`](../../spikes/s5_capacity.py), whose
description says how it measures and what it is given. In short: for each shape, one run at each
number of streams it is given, then one at the class's size, each replaying synthetic agent
sessions of section 4.7's sizes through the gateway as canary students for the duration it is
given, on a pool woken first. Each request is sent as Claude Code sends it: adaptive thinking at its
default effort, `high`, which the pool's `reasoning_effort` mapping rewrites, and the same opening
of 20,000 tokens, Claude Code's instructions and tools, at the start of every session, followed by
the session's own text. It reads what the students got from the load generator's records, and
what each instance's engine measured from the workspace. It never changes the pool.

It posts one run of S5, `measure/S5/<build>-<lever>-<instances>/<part>`, with every number of all
its runs: one number for each quantity and condition, named `<quantity>_<shape>_<streams>`, or
`<quantity>_<shape>_class` at the class's size, the shape `hands_on` or `several_agents`
(`ttft_p95_several_agents_class`), and `class_size`, the class's size the job was given:

| Quantity | Unit | What it is |
| --- | --- | --- |
| `requests`, `failed_requests` | `count` | The requests sent, and those not answered 200 |
| `instances` | `count` | The instances that served the run |
| `ttft_median`, `ttft_p95` | `s` | Time to first token of later turns, as the students saw it |
| `first_turn_ttft_p95` | `s` | The same, of first turns |
| `stream_median`, `stream_p10` | `tokens/s` | A stream's output speed: the median, and the slowest tenth |
| `output_throughput_per_instance` | `tokens/s` | Output tokens an instance's engine produced a second, the mean over the instances |
| `prefill_speed` | `tokens/s` | Tokens the engine computed in prefill, over prefill time, the mean over the instances |
| `cached_share` | `percent` | Input tokens the engine did not compute, the mean over the instances |
| `cache_capacity` | `tokens` | The cache the engine reported at start, the smallest of the instances |
| `running_requests_peak` | `count` | The most requests an instance ran at once |
| `preemptions` | `count` | The engine's preemptions, over every instance; a preemption one instance saw is posted even when another reported nothing, and none is posted as 0 only when every instance reported it |
| `cost_per_million_output_tokens` | `USD per million output tokens` | Each instance's time in service at its configured price, over the output tokens |

A quantity with no sample behind it is not posted for that run.

## The verdict

A job passes when its class-size runs of both shapes each have a 95th-percentile time to first
token of later turns under 5 seconds, a median stream at 15 tokens a second or more, a slowest
tenth at 10 or more, and no preemption. A class-size number that misses its floor, a preemption
among them, fails the job even when another of those numbers is missing. The floors are provisional and are read from the deployed
configuration, the keys `target_ttft_p95_seconds`, `target_stream_median_tokens_per_second` and
`target_stream_p10_tokens_per_second`, whose defaults are those values (sections 7.3 and 17); the
objectives and the inference dashboard read the same keys. The runs at a number of streams are
recorded and do not enter the verdict. Short of a miss, a job whose class-size runs lack one of
those numbers is posted as not measured, as is a job whose runs were served by two builds. The upgrade pool's spike S6 reads the same floors through the same verdict.

## The rows

The record holds the whole matrix: each row is named after its quantity, and its labels say where
it was measured, so the rows of one quantity differ by their labels only. Each row is labelled with
`run`, `pool`, `instance_type`, `build`, `lever`, `instances`, `session_shape` (`hands-on` or
`several-agents`) and `streams` (the number, or `class`); the row `class_size` has all but the last
two. For example:

```toml
[[rows]]
name = "stream_median"
value = 16.5
unit = "tokens/s"
labels = { run = "8bit-baseline-1", pool = "coursework", instance_type = "g7e.2xlarge", build = "8bit", lever = "baseline", instances = "1", session_shape = "hands-on", streams = "8" }
```

The number in this example is invented.

## Running it

No run yet, so the verdict is pending. Running it needs the coursework pool deployed on its GPU
(needs gpu:capacity), and is the owner's; so is the class's size, decision 5 of the design (needs
human:owner-decision), with the session's instances that follow from it (section 4.7).

Each run of the job holds the pool at one number of instances, `RHI_S5_INSTANCES`, and refuses, as
not measured, a run that another number served or that an instance did not serve throughout. The
job is started as a build of `rhi-spike-s5_capacity` on `main`, while nothing else sends to the
pool, with `RHI_SPIKE_ENDPOINT` (the gateway stack's output, a host name reached over HTTPS),
`RHI_SPIKE_WORKSPACE_URL` (the observability stack's output), `RHI_SPIKE_POOL=coursework`,
`RHI_S5_DURATION_SECONDS=<seconds>` and the variables below. Its run label is
`<build>-<lever>-<instances>`.

For each build, `8bit` and then `4bit`:

1. **What one instance serves.** Deploy the coursework pool serving the build, with
   `max_instances = 1`, so that the scaler cannot add a second instance. Start the job with
   `RHI_S5_BUILD=<build>`, `RHI_S5_INSTANCES=1`, `RHI_S5_STREAMS=1,4,8,16` and
   `RHI_S5_CLASS_SIZE=<the students one instance carries in the session>`: the class's size over
   the session's instances, rounded up. Its rows labelled `instances = "1"` are what one
   instance serves, and its class-size runs judge one instance at its share of the class.
2. **The class's size over the session's instances**, when the session needs more than one
   instance. Deploy the pool with `max_instances` at the session's instances, and hold it there for
   the whole job with the scaler's pre-warm, a session window naming that many instances over the
   job's time (section 5.1). Start the job with `RHI_S5_BUILD=<build>`,
   `RHI_S5_INSTANCES=<the session's instances>`, `RHI_S5_CLASS_SIZE=<the class's size>` and
   `RHI_S5_STREAMS=1`, the sweep being the first job's. The configuration's session windows take no
   entry yet: until they do, this job cannot hold the pool and is not run, and the record stays
   pending unless the session needs one instance.
3. **Write the commit's runs into this record**, from the repository's root, with the instance type
   the pool ran:

   ```sh
   gh api --paginate "repos/{owner}/{repo}/commits/<sha>/statuses" |
       env PYTHONPATH=src:services/common:services/gateway:services/reporter:services/engine/lifecycle:spikes \
       uv run --locked python spikes/s5_capacity.py record --commit <sha> --instance-type <type>
   ```

   It reads every page `gh api --paginate` writes, and each run from its newest posting alone: a
   job retried under the same run label is recorded as the retry posted it, never joined to parts
   the earlier attempt left on the commit, even in the same second (the statuses' ids tell them
   apart). A run posted as a pass whose class-size numbers have not all been listed yet is written
   pending, never as a pass; written again once every part is listed, it is the pass. It writes each run of S5 on the commit with
   `tools/measurements/record.py`, then names each row after its quantity and gives it its labels,
   the build, the lever and the instances read from the run label. A run posted as not measured
   becomes a pending run with no row. Add `--run <run label>`, repeated, to write only the runs
   named. A commit whose runs ran on two instance types (a larger instance on the same commit as the
   baseline) is written once for each, each time with `--run` naming that type's runs and
   `--instance-type` giving it: a run the record already holds measured on another pool or instance
   type is refused, and nothing is written.

**The levers** of section 4.7, in their order, each against the baseline run of the same build and
instances (`RHI_S5_LEVER=baseline`, the default). For each, deploy the setting, run steps 1 to 3
with `RHI_S5_LEVER=<lever>`, and deploy the baseline back:

| Lever | `RHI_S5_LEVER` | What is deployed or given |
| --- | --- | --- |
| The 4-bit build | `baseline`, with `RHI_S5_BUILD=4bit` | The pool serving the 4-bit build: the second build above |
| Reasoning effort | `effort-one-lower` | The pool's `reasoning_effort` mapping one step lower for Claude Code's default: `high = "medium"` in the place of `high = "xhigh"`. The job's requests ask for `high`, as Claude Code does, so the engine is asked for the effort the mapping gives |
| A smaller window | `smaller-window` | Nothing on the pool: the job is given `RHI_S5_WINDOW_TOKENS=100000`, and each session compacts as Claude Code does at that window, its next turn starting a new transcript, the opening then a summary of 5,000 tokens of new text, computed in full but for the opening. The baseline's sessions never reach Claude Code's own window of 200,000 tokens |
| The cache | `cache-16bit` | The pool's `kv_cache_bits = 16`, against the 8-bit cache of the baseline |
| The draft head | `draft-head` | The pool's `draft_head_tokens` |
| The step budget | `step-budget` | A smaller `step_budget_tokens` |
| A shared cache salt | `class-salt` | The pool's `cache_salt_scope = "class"`. Every session of the job opens with the same 20,000 tokens, as Claude Code's do, then its own text: with the class's salt the students share the opening's cache, and the first turns and the cached share show the gain against the baseline's per-student salt |
| A larger instance | `larger-instance` | A larger instance type of the same family in the pool |
| More instances | `baseline` | Step 2 at more instances: the run label carries them |
| The faster sibling | `faster-sibling` | The pool serving Qwen3.6-35B-A3B, with `RHI_S5_BUILD` naming its build |
