Spike S11 (system design, section 12) asks two things: does ty, which is beta, give a clean gate on
code written against the current aws-cdk-lib, and do CDK Pipelines accept stages that name no
account and no region?

## The first half: ty on aws-cdk-lib

The gate has passed since the empty app put CDK code in ty's scope (`ty.toml` checks `app.py` and
`src/`, and `scripts/check.sh types` fails on a warning). It passes because, wherever ty misreads
aws-cdk-lib, the line carries a `# ty: ignore[<rule>]` comment with its reason (AGENTS.md). The run
`ty` counts those comments, with ty 0.0.95 and aws-cdk-lib 2.276.0, the pins of `pyproject.toml`,
on the commit above, the `main` commit this record's change starts from: the code it counts is the
same on the commit that lands the record. The parts are:

- `app`: the app's entry point and the constructs of its stage, `app.py` and `src/rhi/` outside
  `src/rhi/pipeline/`;
- `pipeline`: the pipeline stack, `src/rhi/pipeline/`.

The count is the output of:

```sh
grep -rn "ty: ignore" app.py src/rhi
```

There is one comment, in the app: `src/rhi/network/edge.py` passes a load balancer's alias target
to a Route 53 record, and ty reads the generated target's `bind(_record, ...)` as a different
signature from the protocol's `bind(record, ...)`, though jsii passes the argument by position
(`invalid-argument-type`). The pipeline stack needs none.

One comment for one rule is not zero, so the first half is not a perfectly clean gate: it is the
"adjust ty rules" outcome the design foresaw, kept as narrow as it can be, one line and one rule
rather than a rule switched off. A ty or aws-cdk-lib bump that adds or removes such a comment is a
new run of this label.

## The second half: stages with no environment

The app gives no stack an environment: `tests/synth/test_environment_agnostic.py` fails when a
stack of the pipeline or of its stage names an account or a region. Whether CDK Pipelines deploys
such a stage is shown only by the phase 0 deployment (needs aws:deployed-environment). Its answer
is the `deploy/<stage>` commit status of the merge commit that deploys phase 0:

```sh
gh api "repos/{owner}/{repo}/commits/<sha>/statuses"
```

Until it answers, the run `ty` and so the record stay pending. When it does, the owner records
which way it went, here:

- the deployment succeeds with stages that name no environment: the run passes, and so does the
  record;
- it fails: the design's fallback is to give the stages an environment from pipeline variables,
  which is its own change, and this record says so with the run's verdict.
