Spike S1 (system design, section 12) asks, on the coursework pool's instance type: how long each
stage takes from stopped to serving, and from cold; whether the engine image is still on disk after
a stop and start; and how often a stopped instance fails to start. Cold-start time is the central
number of the design: 10 to 13 minutes measured on stock setups, an estimated 2 to 6 minutes from
the warm pool, and 3 to 13 when the pool is empty or its instance fails to start (section 5.2). No
source measured a stopped GPU instance returning to service, or how often one fails to restart for
lack of capacity (evidence E10). If the warm start is not under 5 minutes at the 90th percentile:
bake the image, lower expectations for homework, rely on pre-warm for sessions. The measured start
is also what the launch hook's timeout becomes once configuration holds it (sections 4.3 and 17).

## The job

The job `s1_cold_start` runs [`spikes/s1_cold_start.py`](../../spikes/s1_cold_start.py), whose
description says how it measures and what it is given. In short: for each start, it waits until
the pool is cold and no instance of it still writes, wakes it through the gateway as a canary
student (and repeats the wake every minute, as `rhi wait` does), and times the start from the wake
until the gateway says the pool is ready. It then reads from the workspace the lifecycle agent's
stage metric of the launches that began after the wake, each under its settled transition: a
launch into service is a `promotion` until the host says its disk has no image, and `cold-launch`
after. It never changes the pool or the configuration.

One run measures one kind of start, the kind it is given, and the kind is its label: `warm`, on the
pool as configured, counts the starts whose launch settled as a `promotion`; `cold`, on the pool
deployed with `warm_instances` 0, counts those that settled as a `cold-launch`. A start of the
other kind is printed, and is in no number but the starts run, whether it served or not. A start
failed when a launch of the run's kind was abandoned or not taken into service, when the gateway
reported `capacity_unavailable` on the way (its replacement's timing is not counted), or when the
pool was not ready within 40 minutes and a launch of the run's kind, or none, was seen. A failed
start is counted by the last stage, in launch order, its launch of the run's kind reached by the
deadline, read two minutes after it so that the samples taken before it have reached the workspace
(a stage sampled after the deadline is not counted as reached); with no stage series, `capacity` if
the gateway said so and `unknown` otherwise.

## The rows

Each build of the job posts one run under `measure/S1/<kind>-<build>/<part>`, its label the kind
and CodeBuild's build number (`warm-7`), so that a second build on one commit never leaves a part of
the first behind. Each number below is one row of this record once the spike has run. Every row is
labelled with `run` (the run's label), `pool` (`coursework`), `instance_type` (the type the
counted starts ran on, which the job's log prints) and `kind` (`warm` or `cold`); a row of one
stage also has `stage`, the stage's name in the lifecycle agent's metric, and so does a row of the
starts that failed at one stage. For example, `labels = { run = "warm-7", pool = "coursework", instance_type = "g7e.2xlarge", kind = "warm", stage = "weights" }`.

| Number | Unit | `stage` | What it is |
| --- | --- | --- | --- |
| `start_seconds_median`, `start_seconds_p90` | `s` | | The whole start, from the wake to the pool's `ready` in the gateway's status |
| `boot_seconds_median`, `boot_seconds_p90` | `s` | `boot` | From the kernel's start to the lifecycle agent's |
| `image_seconds_median`, `image_seconds_p90` | `s` | `image` | Reading the metadata and the pool's parameter, and asking the host for the image; a pull too, in a cold launch |
| `release_check_seconds_median`, `release_check_seconds_p90` | `s` | `release-check` | Knowing the release on disk is the pool's current one |
| `container_start_seconds_median`, `container_start_seconds_p90` | `s` | `container-start` | Reading the pool's secret and starting the engine's unit |
| `weights_seconds_median`, `weights_seconds_p90` | `s` | `weights` | Until the engine's health route first answers 200: the weights and the engine's own initialization |
| `warm_up_seconds_median`, `warm_up_seconds_p90` | `s` | `warm-up` | The warm-up request |
| `hook_seconds_median`, `hook_seconds_p90` | `s` | `hook` | Until Auto Scaling answered the completion of the launch hook |
| `starts_run` | `count` | | The starts the run made |
| `starts_counted` | `count` | | The starts of the run's kind that served with no failure: the ones the medians and 90th percentiles are over |
| `starts_failed` | `count` | | The starts that failed |
| `starts_failed_<reason>` | `count` | the stage, for a stage | The starts that failed at that stage (`boot`, `image`, `release_check`, `container_start`, `weights`, `warm_up`, `hook`), or for `capacity`, or for an `unknown` reason |
| `warm_starts_image_zero` | `count` | | A warm run's only: its starts with a promotion that passed its image stage to a later one, so the host held the engine image after the stop and start and nothing was pulled. A promotion abandoned in its image stage is not one |

The medians and 90th percentiles are over the counted starts; a stage no counted start reached has
no row. The whole start holds what no stage does: the time from the wake to the kernel's start,
and the registration and first health check after the hook. The stages sum to the time from the
kernel's start to the completed hook (`services/engine/lifecycle/rhi_lifecycle/stages.py`).

## The verdict

A warm run with fewer than 20 counted starts has no verdict. A warm run passes when
`start_seconds_p90` is under 300 seconds, and fails otherwise. The condition and its 20 starts
judge warm starts only: a cold run, whatever its counted and failed starts, carries the verdict that
this record's warm runs give at the commit the cold run ran from, so that the record's verdict stays
the warm runs' and the cold run's numbers, its timings and its failures, are recorded as theirs are. With no warm run recorded at that commit, the cold
run has no verdict: cold numbers alone never make this record pass. Failed starts are recorded,
not judged: give the job more starts than 20 if some fail.

## Running it

No run yet, so the verdict is pending. Running it needs the coursework pool deployed on its GPU
(needs gpu:capacity), and is the owner's. The owner may lower the pool's `idle_minutes` in the
configuration for the runs, which shortens each cycle: each start waits for the pool to fall idle
and the scaler to return the instance.

1. **Warm.** Start a build of `rhi-spike-s1_cold_start` on `main` with these variables:
   `RHI_SPIKE_ENDPOINT` (the gateway stack's output, a host name the job reaches over HTTPS),
   `RHI_SPIKE_WORKSPACE_URL` (the observability stack's output), `RHI_SPIKE_POOL=coursework`,
   `RHI_S1_KIND=warm`, and `RHI_S1_STARTS` if not 20, while nothing else sends to the pool. Leave
   `RHI_RUN_LABEL` unset, or set it to `warm`: the job posts under `measure/S1/warm-<build>/`.
2. **Record the warm run.** Write the commit's statuses into this record with
   `tools/measurements/record.py`, as the [README](README.md) shows, with `--unit <name>=s` for each
   `_seconds_` number and `--unit <name>=count` for the others. The tool labels each row with `run`
   only: add `pool`, `instance_type` (from the job's log), `kind` and, where the table above gives
   one, `stage` to every row of the run. If the job was built more than once on the commit, keep
   the run you mean to record and delete the others, with their rows. Merge the record.
3. **Cold.** Deploy the coursework pool with `warm_instances` 0, start the job the same way with
   `RHI_S1_KIND=cold`, on a commit of `main` that holds the warm run's record (its statuses are
   `measure/S1/cold-<build>/`), then put `warm_instances` back. Record the cold run as in step 2.

A warm run with no verdict (fewer than 20 counted starts) still posts its numbers, but the tool
records it as a pending run with no row: run it again with more starts, rather than copying its
numbers in. The job's build may take 24 hours: enough for 20 starts that each reach the 40-minute
deadline, with the default `idle_minutes` of 20 before the scaler returns the instance.
