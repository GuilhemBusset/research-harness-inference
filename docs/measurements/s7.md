Spike S7 (system design, section 12) asks, on the mock pool: how long does an idle instance take to
leave service, when terminated and when returned to the warm pool? Does a request in flight survive
a scale-in and a gateway deployment (section 8.5)? Is a wake right after a long idle ever lost?
AWS's documentation does not settle whether a group waits the whole deregistration delay for a
target with no connections, nor whether it drains before stopping an instance into the warm pool
(evidence E13). If it fails: a shorter delay with protection as the only drain, or balancing in the
gateway without the internal load balancer.

## The job

The job `s7_drain` runs [`spikes/s7_drain.py`](../../spikes/s7_drain.py), whose description says how
it measures and what it is given. In short:

- It holds a stream open on the gateway while the owner releases the pipeline again, so that the
  gateway is deployed under it. It holds the stream by sending the request's body slowly and its
  last byte only once the rollout has stopped one of the tasks it began with while a new task was
  writing. A task that only appears, while the old ones go on writing, is not a deployment. It
  starts no stream while more gateway tasks write than the service runs: a deployment is then
  already under way, and the stream could be on one of its new tasks. A completed stream counts
  only when a task it began with still ran as the stream ended, as the task under a stream does
  while it drains. Neither a completed nor a cut stream counts when a new task was writing as it
  opened, or first wrote within a minute after, since the stream may be on that one. Otherwise the
  run is not measured.
- It brings the pool to two instances by load, then lets the pool go idle. From before the scaler
  asks for fewer instances until the first instance it takes away has stopped, it sends whole
  streamed requests, one after another, as one canary student. The job sees the instance gone only
  once its collector has stayed silent, so the requests across the scale-in are told afterwards.
  Neither moment is seen exactly: the scaler asked for fewer between the start of its run and when
  the job read its note, and the instance stopped within a scrape of its last write. A request
  spans the scale-in when it alone was in flight, from its first event from the engine to its end,
  over the whole of one of these spans: requests that follow one another do not show that any one
  of them lived through it. A request that did not complete counts against it when it was in flight
  while the instance was surely leaving; one that ended before, or that the gateway refused (a
  client error), says nothing of the scale-in. The job reads each response as it comes and never
  holds one open itself: what the engine has already sent no longer depends on the instance.
- For each instance the scaler takes away, it counts the seconds from the start of the scaler's
  run that asked for fewer to the instance's collector going silent, that is, to the instance having
  stopped. That is the most it took; the least is from when the job read the note. When these lie
  on either side of 120 seconds, the departure is not told.
- It tells the path by whether the scaler's readings of the warm count, before the note and after
  the stop, rose. Only readings made before the scaler's next decision acted count, since a later
  reading may show the next instance going to the warm pool. A departure whose stop or warm count
  was not seen has no path.
- As many times as it is given, it sends a request at the moment the scaler asks for no instance
  and reads none in service, after the pool's idle period. A reading of none counts only when it is
  at least as recent as the scaler's note asking for none. A lost wake that still woke the pool
  lets it idle back to zero for the next; otherwise the job brings the pool back with requests it
  does not count, and goes on.

It posts, under `measure/S7/<run label>/<part>`, each run under its own label: the job's label
(`RHI_RUN_LABEL`, or `s7-drain`) followed by the build's number, so that a retry on the same commit
leaves the parts of an earlier run readable:

| Number | What it is |
| --- | --- |
| `leave_seconds_terminated` | Seconds an idle instance took to stop when it was terminated |
| `leave_seconds_warm_pool` | Seconds an idle instance took to stop when it went back to the warm pool |
| `stream_completed_scale_in` | 1 when the stream held across the scale-in completed, 0 otherwise |
| `stream_completed_gateway_deployment` | 1 when the stream held across the gateway deployment completed, 0 otherwise |
| `wakes_sent` | Requests sent at the moment the pool reached zero |
| `wakes_lost` | Those that did not complete (answered 200, ending with `message_stop`, no error event) within the pool's hold and a margin |

A run passes when both leave times are 120 seconds or less, both streams completed, and no wake was
lost. A run is not measured if no departure took one of the two paths with a time told, if no request was
across a scale-in, or if no gateway deployment was seen under its first stream, on a task it
began with. The job runs only on the pool named `mock`, and only when its engine is the mock.

## Running it

No run yet, so the verdict is pending. Running it needs the deployed mock pool (needs
aws:deployed-environment), and is the owner's: start a build of `rhi-spike-s7_drain` on `main` with
the variables the script's description lists, release the pipeline again so that the gateway's
deployment begins while the job holds its first stream (it prints when the hold begins, and holds it
for `RHI_S7_DEPLOYMENT_HOLD_SECONDS` at most), then write the commit's statuses into this record with
`tools/measurements/record.py`, as the [README](README.md) shows, with `--unit` set to `s` for the
two leave times and `count` for the other numbers. A run that saw no deployment under that stream
ends with the verdict error and is run again.

The mock's turn is canned, about twenty output tokens, at the rate its engine is given in
`RHI_MOCK_TOKENS_PER_SECOND`, 50 by default: a stream then lasts under a second, while the scaler's
run, within which it asks for fewer, lasts seconds and an instance's stop is known only to within a
scrape (15 seconds). Nothing in a request makes the turn longer, and the job does not change the
pool. So with the mock at its default rate no request spans a scale-in, and every run ends not
measured on that number. Before the run, the owner deploys the mock pool's engine with a rate at
which one turn outlasts a scrape (about one token a second, so twenty seconds a turn), which needs
a change to how the pool's engine is started (needs human:owner-decision), then runs the job.
