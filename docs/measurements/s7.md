Spike S7 (system design, section 12) asks, on the mock pool: how long does an idle instance take to
leave when its session is lowered or ends? Does a request in flight finish within the drain when
its instance is released, and across a gateway deployment (section 8.5)? What does the group do
with an instance still starting when the number is lowered? AWS's documentation settles none of
them: not whether a group waits the whole deregistration delay for a target with no connections,
nor which instance it takes when one is still starting (section 5.1; evidence E13 and E32). If it
fails: a shorter delay with protection as the only drain, or balancing in the gateway without the
internal load balancer; the scaler names the starting instance to terminate.

## The job

The job `s7_drain` runs [`spikes/s7_drain.py`](../../spikes/s7_drain.py), whose description says
what it does in full. It records what it observed, with times, and judges nothing: it writes one
JSON object per line on standard output, which the spike jobs' log group,
`/aws/codebuild/rhi-spikes`, keeps, and posts no number and no verdict. Each line has `at`, the UTC
time to the millisecond, and `kind`; an instance is named `instance-1`, `instance-2`, ... by its
order of appearance in the run, never by its AWS identifier, and an error is recorded by its kind,
never its text.

No request starts a machine, so the job books the mock pool itself, with the module the pipeline's
verification and spike S8 book with (`scripts/pipeline/booking.py`): two instances, under the name
`spike/s7_drain`, for the minutes it is given. It does not start when the pool has a session booked
or active, or allows fewer than two instances (`refused`). It moves the pool only by changing its
own session, each write a `session` line (`booked`, `lowered`, `stopped`, and whether it was
written), and it stops the session it holds when it ends, whatever came of the run. Its four steps:

1. **The stream across a gateway deployment.** It holds a stream open on the gateway
   (`hold_started`, then a `stream` line, `gateway_deployment`): it sends the request's body but
   its last byte, then a byte of white space every few seconds, and the last byte when the time is
   over. The job starts no deployment and reads none: the owner starts it against a release that
   is already past the pipeline's hold, and checks afterwards that the two overlapped ("Running
   it", below).
2. **The departures.** Once the scaler reads two instances in service (`instances`), the job lowers
   its session to one and records the instance that leaves; then it stops its session and records
   the last one. It stops its session once the first departure is whole, the scaler's note reads
   the instance out of the group and the instance that stays was read writing a minute after that
   note, or the wait ran out (`timeout`, `departure_confirmed`): the note counts instances without
   naming them, and a collector read silent may be the one of the instance that stays, at a time
   the workspace shows no write for. For each decision it writes when the
   scaler's note asked for fewer (`scale_in_asked`) and when it first read the scaler's in-service
   count drop (`out_of_service`, one line for each decision the reading shows a drop of); for
   each instance that left, when it first read its collector silent (`gone`, or `gone_withdrawn`
   when a later read shows a write after it: the collector kept writing), and the departure
   whole, the instance with those three times (`scale_in`). The `scale_in` lines are written as
   the step ends, one for each instance that left: a stop that was withdrawn has none, and a stop
   from before a decision's note is not that decision's.
3. **The stream across a release.** Before it lowers its session it opens one request and holds its
   body open at the gateway: it lowers only once the request's first part is sent. It sends the
   last byte as soon as it reads, after its own lowering, the scaler's note that asks for fewer,
   for the one instance it lowered to, so that the gateway forwards the request to the pool while
   the group takes the departing instance out of service, and reads the answer to its end (a
   `stream` line, `release`, whose `body_sent_at` is when it was forwarded). If that note is not
   read before the wait runs out, or the first note that asks for fewer asks for another number
   (the session ended before the scaler acted on the lowering), the last byte is never sent, and
   the line says so (`body_unsent`, with no `body_sent_at` and no decision).
4. **The starting instance.** Once the note reads the pool at zero, the job books two instances
   again, and lowers its session to one as soon as the note reads one instance in service and one
   starting. One line, `starting_instance`, says which of the two left, `starting` or
   `in_service`, and when: the times of the note that read the state, of the lowering, of the
   first note that reads one of the two gone (`left_written_at`) and of the first that reads it
   out of the group (`gone_written_at`), and, when the instance's collector had written, its name
   and its last write. The job names the instance whose collector stopped only once the other was
   read writing a minute after the note that reads one out of the group: before that, the silent
   collector may be the one of the instance that stays, at a time the workspace shows no write
   for. When the wait for it runs out, the line names no instance and holds what the notes told.
   The role is told only where a reading tells it, and the line holds both readings
   (`left_by_notes`, `left_by_launches`):
   - the notes tell that the one in service left, when the first note after the lowering that
     reads fewer than two reads none in service and one starting. A note that reads one in service
     and none starting tells neither: the starting one left, or it entered service and the other
     left between two notes, which count instances without naming them;
   - the launches tell either. Each instance's lifecycle agent says of its own launch, in the
     workspace, that it started and that its hook is completed, before which no instance is in
     service. An instance read at the lowering or after it with its launch started and its hook
     not completed was the starting one (`starting_when_lowered`), and the other the one in
     service: the instance whose collector stopped is one or the other, and when none stopped and
     the starting one alone ever wrote, the one in service left before its collector wrote. The
     line also says when the hook of the instance that stopped was first read completed
     (`hook_completed_at`), null when it never was: the starting one may have completed it
     between the lowering and its leaving.

   `left` is null, with the `reason`, when the state was never read (`state_not_read`), nothing
   left, both were read in service before one left, the readings disagree, or neither tells
   (`role_not_told`): the line then still names the instance that left, with its times. Neither
   tells when the starting instance's collector had not written by the time it left, or when its
   hook was completed before the lowering, the instance not yet in service. When a collector
   first wrote tells no role: it starts apart from the agent. Whoever reads the pass condition
   from the run decides what more a line that tells no role takes.

A wait that runs out is a `timeout` line that says what was waited for, and the job goes on with
what it read. Each stream's line holds when it was sent and its body sent whole, when its first and
its last event arrived, the events it received, and how it ended: `closing_event` (it finished),
`error_event`, `connection_closed` (it was cut), `http_status` with the status, `timeout`, or
`body_unsent`.

## What the job is given

| Variable | What it is |
| --- | --- |
| `RHI_SPIKE_ENDPOINT` | The gateway's address, the gateway stack's output |
| `RHI_SPIKE_WORKSPACE_URL` | The Prometheus workspace's query address, the observability stack's output |
| `RHI_SPIKE_POOL_STATE_TABLE` | The name of the stage's pool-state table, the pools stack's output |
| `RHI_SPIKE_RUN_MINUTES` | The minutes the job books the pool for, from its start: required, a whole number of one or more |
| `RHI_S7_DEPLOYMENT_SECONDS` | How long the stream across the gateway deployment is held: 1500 unless given |

The minutes are the whole run's: the stream across the deployment, then the waits of the other
steps, each bounded at twenty minutes. About an hour and a half covers a run in which no wait runs
out; the minutes are at most the configuration's `session_max_hours`. The job stops its session
when it ends, so minutes it does not use cost nothing, and a job that dies leaves a session that
ends by itself after them. The pool's engine and `max_instances` come from the deployed
configuration.

## Running it

No run yet, so the verdict is pending. The job is run once the scaler releases the instances of a
lowered session (issue E6-15): before that is deployed, a lowered session releases nothing by
itself, the waits of steps 2 to 4 run out, and instances leave only when the session is stopped.

Running it needs the deployed mock pool (needs aws:deployed-environment), and is the owner's. The
pipeline holds a stage's deployment while a session is active on any pool, the job's own on the
mock pool included (system design, section 8.2, step 5). A release made once the job has booked
waits until the job has stopped its session, and nothing is deployed under its first stream. So the
release comes first:

1. While no session is booked or active on any pool, release a change that replaces the gateway's
   task, such as a merge that changes the gateway's code or its task definition. Releasing an
   unchanged commit again replaces nothing.
2. Wait until that execution's action `Hold` has succeeded: from then on the job's session cannot
   hold it. Then start a build of `rhi-spike-s7_drain` on `main`, with the variables above. The
   gateway's stack is deployed after the four it reads from, and the build needs a minute or two
   before its first lines, `session` and `hold_started`: step 3 says whether the stream was open
   in time.
3. Check that the deployment and the stream overlapped, in the account, from the gateway service's
   own record of its deployment: when the deployment started, and when the service began to drain
   its old task. The `stream` line `gateway_deployment` crossed the deployment when its `sent_at`
   is earlier than the deployment's start, so that the stream was on the task that was replaced,
   and its `body_sent_at` is later than the moment the old task began to drain. With a `sent_at`
   later than the deployment's start the stream may be on the new task, and the line then says
   nothing of a deployment: the first step is read from another build, started the same way.

The execution's verification follows the deployment, which is complete only once the old task is
gone, so after the first stream has ended: the job is then in its second step. The verification
tests the mock pool with the session that is there, the job's, by a few short requests, and its
tests fail on that execution if no instance of the job's is in service just then. If it comes
while the job holds no session, between its second step and its fourth, it books the pool itself:
the fourth step then waits for a pool at zero or finds the pool booked, and its line says so
(`pool_not_at_zero`, `not_booked`). The steps a release disturbed are read from a build started
while no execution runs, with `RHI_S7_DEPLOYMENT_SECONDS` set to a minute: its first stream
crosses nothing, and its other steps are undisturbed.

The log of a build then holds: `hold_started` and the `stream` line `gateway_deployment`;
`scale_in_asked`, `out_of_service`, `gone` and `scale_in` for two departures; the `stream` line
`release`; one `starting_instance` line; and `run_ended`. The mock pool's session reads as ended
afterwards. The pass condition is read from those lines later, by an issue written then (system
design, section 12).

The mock's turn is canned, about twenty output tokens, at the rate its engine is given in
`RHI_MOCK_TOKENS_PER_SECOND`, 50 by default: a stream read as it comes lasts under a second, while
an instance's stop is known only to within a scrape (15 seconds). The job does not change the
pool's engine, so the line of the stream across the release says whether, and how long, its answer
outlasted the scaler's decision.
