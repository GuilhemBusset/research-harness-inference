Spike S7 (system design, section 12) asks, on the mock pool: how long does an idle instance take to
leave service, when terminated and when returned to the warm pool? Does a request in flight survive
a scale-in and a gateway deployment (section 8.5)? Is a wake right after a long idle ever lost?
AWS's documentation does not settle whether a group waits the whole deregistration delay for a
target with no connections, nor whether it drains before stopping an instance into the warm pool
(evidence E13). If it fails: a shorter delay with protection as the only drain, or balancing in the
gateway without the internal load balancer.

## The job

The job `s7_drain` runs [`spikes/s7_drain.py`](../../spikes/s7_drain.py), whose description says
what it does and what it is given. It records what it observed, with times, and judges nothing: it
writes one JSON object per line on standard output, which the spike jobs' log group,
`/aws/codebuild/rhi-spikes`, keeps, and posts no number and no verdict. Each line has `at`, the UTC
time to the millisecond, and `kind`; an instance is named `instance-1`, `instance-2`, ... by its
order of appearance in the run, never by its AWS identifier, and an error is recorded by its kind,
never its text. In short:

- It holds a stream open on the gateway (`hold_started`, then a `stream` line, `gateway_deployment`)
  while the owner releases the pipeline again: it sends the request's body but its last byte, then
  a byte of white space every few seconds, and the last byte when the hold is over.
- It brings the pool to two instances by load, then lets the scaler take it back to none by
  idleness, in two steps or at once. For each decision it writes when the scaler's note asked for
  fewer (`scale_in_asked`) and when it first read the scaler's in-service count drop
  (`out_of_service`); for each instance that stopped, when it first read the collector silent
  (`gone`, or `gone_withdrawn` when a later read shows the collector kept writing), and the
  departure whole with its path, `terminated`, `warm_pool`, or `unknown` with the
  reason when the readings of that decision do not agree (`scale_in`). The warm count is read for
  at least five minutes past the stop, and up to the scaler's next decision, before a path is told,
  since a return to the warm pool may be counted late; either path is told only from readings
  that reach the end of that time and miss none of the scaler's runs within it, since a missing
  run may hold a fall in the count. A cycle that did not show both paths is run again, once.
- In the first cycle, it opens one request as the load stops, before the scaler asks for fewer,
  and holds its body open at the gateway; it sends the body whole as soon as it reads the scaler's
  first decision, so that the gateway forwards it to the pool while the group takes the departing
  instance out of service and before that instance stops, and reads its answer to its end (a
  `stream` line, `scale_in`, whose `body_sent_at` is when it was forwarded).
- As many times as it is given, it sends one request at the moment the pool reads zero after its
  idle period, each at a fresh zero, and writes the times of the zero, of the request, of the
  scaler's next note asking for capacity and of the engine's first event, the gateway's keep-alives
  told apart, or that none came within the pool's hold (`wake`).

Each stream's line holds when it was sent and its body sent whole, when its first and its last
event arrived, the events it received, and how it ended: `closing_event`, `error_event`,
`connection_closed`, `http_status` with the status, or `timeout`.

## Running it

No run yet, so the verdict is pending. Running it needs the deployed mock pool (needs
aws:deployed-environment), and is the owner's: start a build of `rhi-spike-s7_drain` on `main` with
the variables the script's description lists, and release the pipeline again while the job holds
its first stream (its `hold_started` line says until when). Its log then holds the lines of both
scale-in paths, both held streams and the wakes. The pass condition is read from those lines later,
by an issue written then (system design, section 12).

The mock's turn is canned, about twenty output tokens, at the rate its engine is given in
`RHI_MOCK_TOKENS_PER_SECOND`, 50 by default: a stream read as it comes lasts under a second, while
an instance's stop is known only to within a scrape (15 seconds). The job does not change the pool
or its engine, so the line of the stream across the scale-in says whether, and how long, its answer
outlasted the scaler's decision.
