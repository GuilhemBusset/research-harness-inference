Spike S7 (system design, section 12) asks, on the mock pool: how long does an idle instance take to
leave service, when terminated and when returned to the warm pool? Does a request in flight survive
a scale-in and a gateway deployment (section 8.5)? Is a wake right after a long idle ever lost?
AWS's documentation does not settle whether a group waits the whole deregistration delay for a
target with no connections, nor whether it drains before stopping an instance into the warm pool
(evidence E13). If it fails: a shorter delay with protection as the only drain, or balancing in the
gateway without the internal load balancer.

## The job

The job `s7_drain` runs [`spikes/s7_drain.py`](../../spikes/s7_drain.py), whose description says how
it measures and what it is given. In short: it holds a slow stream open while the owner releases the
pipeline again, so that the gateway is deployed under it; it brings the pool to two instances by
load, then lets it go idle, holding a slow stream across the first scale-in; for each instance the
scaler takes away, it counts the seconds from the scaler's note asking for fewer to the instance's
collector going silent, that is, to the instance having stopped, and tells the path by whether the
warm count rose; then, as many times as it is given, it sends a request at the moment the scaler asks
for no instance after the pool's idle period.

It posts, under `measure/S7/<run label>/<part>`:

| Number | What it is |
| --- | --- |
| `leave_seconds_terminated` | Seconds an idle instance took to stop when it was terminated |
| `leave_seconds_warm_pool` | Seconds an idle instance took to stop when it went back to the warm pool |
| `stream_completed_scale_in` | 1 when the stream held across the scale-in completed, 0 otherwise |
| `stream_completed_gateway_deployment` | 1 when the stream held across the gateway deployment completed, 0 otherwise |
| `wakes_sent` | Requests sent at the moment the pool reached zero |
| `wakes_lost` | Those not answered 200 within the pool's hold and a margin |

A run passes when both leave times are 120 seconds or less, both streams completed, and no wake was
lost. A run in which no departure took one of the two paths is not measured.

## Running it

No run yet, so the verdict is pending. Running it needs the deployed mock pool (needs
aws:deployed-environment), and is the owner's: start a build of `rhi-spike-s7_drain` on `main` with
the variables the script's description lists, release the pipeline again while the job prints that
it holds its first stream, then write the commit's statuses into this record with
`tools/measurements/record.py`, as the [README](README.md) shows, with `--unit` set to `s` for the
two leave times and `count` for the other numbers. The gateway deployment's time, from the
pipeline, should fall inside the hold the job printed; a run where it did not says nothing of the
gateway deployment and is run again.
