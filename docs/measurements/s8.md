Spike S8 (system design, section 12) asks, on the mock pool, in a session of two instances in two
zones: does a replayed stickiness cookie keep one student on one instance, and move when that
instance leaves? AWS lists a healthy target in every zone as a requirement for stickiness, which a
pool of one or two instances over three zones does not have, and the gateway replaying each
student's cookie (section 5.5) has not been tried (evidence E13, known gap 10). If it does not
hold, a pool stays at one instance until it does, and a class that needs more runs on the upgrade
pool, whose single instance needs no affinity (section 5.5).

## The job

The job `s8_stickiness` runs [`spikes/s8_stickiness.py`](../../spikes/s8_stickiness.py), whose
description says how it measures and what it is given. In short: it books the mock pool itself, a
session of two instances for the minutes it is given, and sends nothing until the scaler's note
asks for two and reads two in service; it then holds streams open through the gateway until both
instances serve, and records the zones of the two; two canary students then send their first
requests at once and their other requests one after another; the job lowers its session to one
instance and sends nothing until the scaler's note asks for one and reads one in service, and the
students send their requests again. When it ends, whatever came of the run, it stops its session.
It does not start on a pool that has a session booked or active, or that allows fewer than two
instances, and it changes and stops only a session that still reads as its own. Which instance
served each request is read from the workspace, and whose first request each instance served from
the mock's cache imitation: a student's second request has its first's whole input cached only on
the instance that served the first. A phase in which the pool's rebalance number changed is
measured again.

It posts, under `measure/S8/<run label>/<part>`:

| Number | What it is |
| --- | --- |
| `zones` | The zones the two instances were in |
| `student_<n>_<phase>_sent` | The requests student 1 or 2 sent in the phase `before` (its first request included) or `after` the departure |
| `student_<n>_<phase>_most_served` | The most of them any one instance served |

A run passes when, for each student and phase, the most any one instance served is every request
the student sent; after the departure, that instance is the one that stayed. A run whose two
instances were in one zone posts its numbers with no verdict (the state error): it does not answer
the question. A run is not measured, and posts no number, when an instance left during the phase
before the departure (a split student's phase is checked again a few minutes later, so that a
departure the workspace showed late does not count as a failure), or when the two students were on
one instance before the departure, so that neither, or both, had to move rather than one moving
while the other stayed.

## The first run

The first run, on 2026-11-27, ran the job on the mock pool with ten requests per measured student
and a 90-minute session, on the commit its record names. It booked two instances and held 16
streams, as 6 students, 0.30 s apart, until two instances were in service in two zones. The phase
before the departure was disturbed on the first attempt (a student's requests split across the
instances while the in-service count was checked again), so the job measured it again, as the
job's description says. Then each measured student's 10 requests, after the opening one, stayed on
one instance. The job lowered its session to one instance: one student's instance stayed and the
other's left, and after the departure each student's 10 requests went to the remaining instance.
The job stopped its session, and the pool then read no session.

The verdict is pass: every request of a student reached one instance until that instance left, and
the student whose instance left moved to the one that stayed. The numbers are in the front matter:
the before-phase rows count the opening request, 11 sent and 11 served by one instance, and the
after-phase rows count 10 and 10. One run on the mock pool, with two students measured, is what
the spike asks; it does not measure a pool of more instances or a longer session.

## Running it

A run needs the deployed mock pool (needs aws:deployed-environment), and is the owner's: start a
build of `rhi-spike-s8_stickiness` on `main` with the variables the script's description lists,
`RHI_SPIKE_RUN_MINUTES` among them, the minutes the job books the pool for, which it requires.
Then write the commit's statuses into this record with `tools/measurements/record.py`, as the
[README](README.md) shows, with `--unit zones=count` and the unit `count` for each student's
numbers.

After a run, whatever came of it, the owner checks that the job left the mock pool with no session
booked or active, with the admin CLI (`rhi_admin` is the name the runbook
[`sessions.md`](../runbooks/sessions.md) defines for it):

```sh
rhi_admin session status
```

In the pools' lines, the mock pool's column `session` must read `none`. The command shows a pool's
session, and who set it, only while one is booked or active: a session the job stopped, or one that
ended by itself, reads `none`, with `-` under `set_by`. A line that still shows a session under
`spike/s8_stickiness` is one the job did not stop: it ends by itself after its minutes, or is
stopped with `rhi_admin session stop --pool mock`.
