Spike S8 (system design, section 12) asks, on the mock pool with two instances in two zones: does
a replayed stickiness cookie keep one student on one instance, and move when that instance leaves?
AWS lists a healthy target in every zone as a requirement for stickiness, which a pool of one or
two instances over three zones does not have, and the gateway replaying each student's cookie
(section 5.5) has not been tried (evidence E13, known gap 10). If it does not hold, a pool stays at
one instance until it does, and a class that needs more runs on the upgrade pool, whose single
instance needs no affinity (section 5.5).

## The job

The job `s8_stickiness` runs [`spikes/s8_stickiness.py`](../../spikes/s8_stickiness.py), whose
description says how it measures and what it is given. In short: it holds streams open through the
gateway until the scaler has added the pool's second instance, and records the zones of the two;
two canary students then send their first requests at once and their other requests one after
another; the job sends nothing until the scaler has taken the pool back to one instance, and the
students send their requests again. Which instance served each request is read from the
workspace, and a phase in which the pool's rebalance number changed is measured again.

It posts, under `measure/S8/<run label>/<part>`:

| Number | What it is |
| --- | --- |
| `zones` | The zones the two instances were in |
| `student_<n>_<phase>_sent` | The requests student 1 or 2 sent in the phase `before` or `after` the departure |
| `student_<n>_<phase>_most_served` | The most of them any one instance served |

A run passes when, for each student and phase, the most any one instance served is every request
the student sent; after the departure, that instance is the one that stayed. A run whose two
instances were in one zone posts its numbers with no verdict (the state error): it does not answer
the question.
