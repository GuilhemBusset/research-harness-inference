Spike S4 (system design, section 12) asks how long the coursework model's 31 GB of weights take to
load from S3 with the loader tuned. AWS measured 15 GB in about 5 seconds and 200 GB in about 25
seconds with the Run:ai streamer tuned, but defaults can be ten times slower, one model was
reported slower than the plain loader, and those timings come from an instance with far more
network bandwidth than a single-GPU type has (sections 4.4 and 5.2; evidence E11). The cold-start
budget estimates 20 to 100 seconds for this stage (section 5.2). If the streamer does not load the
weights in under 100 seconds, the pool's loader becomes download, then load: the pool's `loader`,
`stream` or `download`.

## The job

The job `s4_weights` runs [`spikes/s4_weights.py`](../../spikes/s4_weights.py), whose description
says how it measures and what it is given. In short: for each start, it waits until the pool is
cold and no instance of it still writes, wakes it through the gateway as a canary student, waits
until it is ready, and reads from the workspace the weights stage of the lifecycle agent's metric
for the one launch into service that completed its hook after the wake and whose instance was still
running when the pool became ready. Each value is read in one query with the time of its own
sample, so a late scrape cannot pass an earlier launch's value off as this start's. It never
changes the pool.

Each loader setting is a configuration the owner deploys, and its name is the run's label: one run
per setting. It posts, under `measure/S4/<loader setting>/<part>`:

| Number | Unit | What it is |
| --- | --- | --- |
| `starts` | `count` | The starts made |
| `weights_seconds_median` | `s` | The median of their weights stages: from the engine's start to its health route's first 200 |

A run passes when the median is under 100 seconds. Each row is labelled with `run` (the loader
setting's name), `pool` and `loader` (the setting again), for example
`labels = { run = "stream", pool = "coursework", loader = "stream" }`. The weights stage also
holds the engine's own initialization, which the agent cannot tell apart from the load
(`services/engine/lifecycle/rhi_lifecycle/stages.py`).

## Running it

No run yet, so the verdict is pending. Running it needs the coursework pool deployed on its GPU
(needs gpu:capacity), and is the owner's. For each loader setting to compare (`stream`, then
`download`, or a tuned streamer under a name of its own):

1. Deploy the coursework pool with that setting in its configuration.
2. Start a build of `rhi-spike-s4_weights` on `main` with these variables:
   `RHI_SPIKE_ENDPOINT` (the gateway stack's output, a host name the job reaches over HTTPS; the
   job refuses any address that is not HTTPS), `RHI_SPIKE_WORKSPACE_URL` (the observability
   stack's output), `RHI_SPIKE_POOL=coursework`, `RHI_S4_STARTS=<starts>` and
   `RHI_S4_LOADER=<setting>`, while nothing else sends to the pool.
3. Write the commit's statuses into this record with `tools/measurements/record.py`, as the
   [README](README.md) shows, with `--unit starts=count --unit weights_seconds_median=s`, then add
   the labels `pool` and `loader` to the run's rows.

Then set the coursework pool's `loader` to the faster setting in the deployed configuration.
