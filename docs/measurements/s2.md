Spike S2 (system design, section 12) asks, on the mock pool: does each client survive a 7-minute
held stream and a 4-minute held call, Codex with its default timer and with the profile `rhi login`
writes? Claude Code tolerates a stream of pings for about 12 minutes; Codex's idle timer ignores the
gateway's keep-alive comments and stops a stream after 300 seconds by default, which is why the
profile sets a 15-minute stream timeout; the SDKs time a whole call out at 10 minutes (section 5.3,
evidence E12). If a client aborts with the profile in place, that client gets a shorter hold, and
`rhi wait` is documented for it. Codex with its default timer is expected to abort: that does not
fail the run.

The two budget causes are answered 402, which the SDKs do not retry, so that they reach the student
at once. How each client shows a 402 is part of this spike (section 6.2, step 8).

## The job

The job `s2_client_hold` runs [`spikes/s2_client_hold.py`](../../spikes/s2_client_hold.py), whose
description says how it measures and what it is given. In short: it installs the pinned harnesses
([`spikes/harnesses.py`](../../spikes/harnesses.py)) and prints the version of each harness and
SDK; it sends each client one request as the canary student whose daily budget is 0, and confirms
the gateway answered it 402 `budget_reached`; it then starts the five streams at once on a cold
pool, and later the two non-streaming calls just under 4 minutes before the pool is ready. Each
client reaches the gateway through a local forwarder that records its requests and directs them to
the mock pool. A hold counts only when the pool became ready less than the pool's deadline, and no
more than 60 seconds less, after the client's request, and when the client, not the gateway, ended
the request; a client whose hold was not that one is run again on the next cold start. Each build
posts under a run label of its own, which its log prints: `s2-client-hold-` and a random suffix,
unless the owner gives one in `RHI_RUN_LABEL`.

## The rows

Once the spike has run, the record holds one row per number the job posts, each labelled with the
run, the client, its version and the kind of call (`stream`, or `call` for a non-streaming call).
The versions the job is pinned to are below; the run's own log prints the ones it ran.

| Client | Version | Kind of call | Rows |
| --- | --- | --- | --- |
| `claude_code`, Claude Code | 2.1.323 | stream | `claude_code_stream_completed`, `claude_code_stream_seconds_before_giving_up` |
| `codex_default`, Codex with its default timer | 0.169.0 | stream | `codex_default_stream_completed`, `codex_default_stream_seconds_before_giving_up` |
| `codex_profile`, Codex with the profile of `rhi login` | 0.169.0 | stream | `codex_profile_stream_completed`, `codex_profile_stream_seconds_before_giving_up` |
| `openai_sdk`, the OpenAI SDK script | 3.57.0 | stream | `openai_sdk_stream_completed`, `openai_sdk_stream_seconds_before_giving_up` |
| `openai_sdk`, the OpenAI SDK script | 3.57.0 | call | `openai_sdk_call_completed`, `openai_sdk_call_seconds_before_giving_up` |
| `anthropic_sdk`, the Anthropic SDK script | 2.11.0 | stream | `anthropic_sdk_stream_completed`, `anthropic_sdk_stream_seconds_before_giving_up` |
| `anthropic_sdk`, the Anthropic SDK script | 2.11.0 | call | `anthropic_sdk_call_completed`, `anthropic_sdk_call_seconds_before_giving_up` |

`completed` is 1 when the whole answer reached the client and the client exited without error, and
0 otherwise; `seconds_before_giving_up` is the seconds from the client's request to the moment it
gave up, 0 for a request that completed. A client that dropped its request and sent it again gave
up at the drop.

`retried` is 1 when the client sent its refused request again; `shown` is 1 when what it printed
holds the cause's sentence or its name `budget_reached`.

## Running it

No run yet, so the verdict is pending. Running it needs the deployed mock pool (needs
aws:deployed-environment), and is the owner's:

1. Set the mock pool's `start_delay_seconds` in the configuration in SSM, so that a cold start of
   the pool through the gateway lasts just under its `hold_seconds` (420 seconds by default): about
   400 seconds, less the time the pool takes to launch and register an instance. The release passes
   the delay to the mock only when the pipeline deploys (`rhi.pools.release`): let the pipeline run
   on `main` and wait for its `deploy/<stage>` status on that commit before the next step.
2. Start a build of `rhi-spike-s2_client_hold` on `main`, with `RHI_SPIKE_ENDPOINT` set to the
   gateway's address, and nothing else sending to the mock pool.
3. Remove `start_delay_seconds` from the configuration in SSM, and let the pipeline deploy again.
4. Write the commit's statuses into this record with `tools/measurements/record.py`, as the
   [README](README.md) shows, with the unit `count` for the `completed`, `retried` and `shown`
   numbers and `s` for the seconds, then add the labels `client`, `version` and `call` to each row
   from the job's log.

A run that is not measured (a hold that never fell just under its deadline, a client that never
reached the 402) says why in its log; the delay is then adjusted and the job run again.
